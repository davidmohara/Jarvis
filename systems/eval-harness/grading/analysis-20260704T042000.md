## Tier Analysis

### Tier 1: Mechanical

33 of 52 records (63%) report `completed: true`. 11 records are aborted (all general-purpose or one system-eval). 8 records are partial — notably, all morning-briefing records with strong A/B grades are partial, suggesting the `partial` status is a scheduling/termination artifact rather than a quality failure. Average tool failures across the corpus: 0.06 (very low — tool-level reliability is not an issue).

### Tier 2: Structural Assertions

42 of 52 records (81%) have assertions evaluated. Average pass rate: 72.5%. The most commonly failing assertions are:

- **daily-review daily-005** (wins/completed section): Fails on 12+ of 23 daily-review runs. Reviews discuss completions in prose ("eleven OmniFocus completions") but don't use the pattern `completed|done|accomplished|finished|wins` in isolation. This is a false-negative — the assertion definition is too narrow.
- **daily-review daily_review-wm-written** (working memory for run date): Fails on approximately 8 runs. Some daily-review runs produce the review file but skip writing working memory (2026-06-30 is a confirmed example).
- **system-eval system-eval-001** (state.yaml status: complete): Fails on 5 of 7 system-eval records. This is a timing artifact — by the time assertions run on a previous record, the current run has already overwritten state.yaml to `in-progress`. The assertion is checking a file that changes after the run completes.
- **system-eval system-eval-009** (working memory content): Fails on all 7 system-eval records. System-eval does not write a working memory file — this assertion checks for something the workflow never produces.

## Patterns Identified

1. **daily-review output-write failure (7/23 runs, 30%):** Records eval-20260530T021202-MKO2P3, eval-20260602T021149-SL6FJ9, eval-20260605T021223-ARZ3WN, eval-20260613T021205-CFZ2ZA, eval-20260620T021321-T6V6WJ, eval-20260627T021053-VB6Z9C, and eval-20260704T021304-XNRG5T all have duration_seconds: 0.0 and produce no review file. The workflow is being triggered but not executing. Identified in the 2026-06-27 analysis as the top recommendation — still unresolved. This is now a 7-week-old unresolved regression.

2. **daily-review wins assertion (daily-005) systematically underperforms:** Fails on approximately 14 of 23 runs (61%). The assertion pattern `completed|done|accomplished|finished|wins` misses prose-embedded completions like "eleven OmniFocus completions" or "one completion." This generates false-negative grades and depresses scores across the entire daily-review history. This is an assertion definition problem, not a workflow quality problem.

3. **general-purpose records are all aborted/failed debug sessions:** 9 records, all status: aborted or the equivalent, all score at floor (0.17–0.375). Six of these clustered on 2026-06-19, suggesting a session crash. These records add noise to the corpus but don't represent a workflow with structured purpose. They should be excluded from workflow-level trend analysis or archived.

4. **morning-briefing consistently reports partial status despite A/B output quality:** 4 of 5 morning-briefing runs are partial. All produce substantive, well-structured output. The partial status is likely a workflow state-write timing issue (session ends before the final state update). The assertion pass rate (100% on the runs with assertions) confirms output quality is not the issue.

5. **system-eval assertion timing flaw (persistent):** Assertions 001 and 009 in the system-eval assertion definition are structurally broken: 001 checks a file that gets overwritten before assertions can run, and 009 checks for a file the workflow never produces. Both have been failing since the first system-eval run. They inflate the "records_with_failures" count and depress system-eval scores artificially.

6. **Tier 4 controller feedback critically absent (87% of records have no feedback):** The eval system is operating without the most important quality signal. Scores computed without Tier 4 feedback redistribute weight to mechanical and structural tiers, which can mask quality issues that only David would catch.

7. **daily-review quality trend: strong improvement since June 17:** May 30 through June 13 saw 5 consecutive F-grade runs (output-write failures). Since June 17, only 2 failures in 8 runs — today's zero-duration run and the June 27 run. The underlying workflow is performing well when it actually runs.

## Recommendations

1. **[CRITICAL — 7 weeks old] Add output-write guard to daily-review step-auto.** The workflow invocation is reaching the agent but execution isn't happening (duration_seconds: 0.0 on all failing runs). Inspect the scheduled trigger, the agent handoff, and whether the session reaches the write step before terminating. A guard that explicitly fails the eval record if the output file doesn't exist within 60 seconds of step-auto completion would surface this immediately.

2. **[ASSERTION FIX] Update daily-005 assertion pattern for daily-review.** Change pattern from `completed|done|accomplished|finished|wins` to include `OmniFocus|completion|finished|closed|wrapped|accomplished|achieved|wins`. Or restructure the assertion to check for quantified output language (a number followed by "task" or "item"). Current pattern generates false negatives on 61% of runs.

3. **[ASSERTION FIX] Remove or fix system-eval assertions 001 and 009.** Assertion 001 (state.yaml status: complete) should check a timestamped snapshot or the prior run's state, not the live file. Assertion 009 should be removed — system-eval does not write working memory and there is no plan to add it.

4. **[DATA HYGIENE] Archive general-purpose records from 2026-06-19 cluster.** The 6 aborted records (0M80W7, KEZHL6, YUFRKN, POVPT0, W7DPHP, FY9JS4) are debug/crash artifacts that don't represent structured workflow runs. Move to `systems/eval-harness/runs/archive/` to clean up the corpus and improve average score accuracy.

5. **[MISSING WORKING MEMORY] Add working memory write verification to daily-review.** The 2026-06-30 run (XWZAFG) produced a quality review file but no working memory. This means the next session doesn't have continuity context from that day. Add a check at step-auto close that verifies both the review file and working memory were written before reporting success.

6. **[TIER 4] Prompt David for controller feedback on top-performing recent records.** Specifically: eval-20260625T021317-18HGDJ (daily-review A, 0.96), eval-20260623T021234-DH9VSD (daily-review A, 0.96), and eval-20260702T021204-2E3TK4 (daily-review B, 0.92). These are the clearest candidates for positive feedback that would calibrate the scoring model.

7. **[STATUS FIX] Investigate morning-briefing partial status.** 4 of 5 runs report partial. If the briefing output is complete, the status should be success. Check whether morning-briefing closes its state.yaml before the session terminates — the partial status may be from a timeout cutting off the final state write.
