## Patterns Identified

1. **Daily-review output-write failure (5/19 runs, persistent):** Runs on 2026-05-30, 2026-06-02, 2026-06-05, 2026-06-13, 2026-06-20, and 2026-06-27 produced no output file despite status: success. The June 27 run is the most recent — today's scheduled run failed silently. This is the single highest-impact structural failure in the corpus. Evidence: reviews/daily/ contains no auto-2026-06-27.md; memory/working/ contains no daily-review-2026-06-27 entry; assertion_results confirm all output checks failed.

2. **Daily-review state.yaml YAML parse error (12/19 runs):** The assertion `Daily review workflow state.yaml shows status: complete` fails on every run where the state.yaml file contains multiple YAML documents (a multi-doc format with `---` separators). This is a false failure — the workflow is completing correctly, but the assertion engine's yaml.safe_load rejects multi-document YAML. Evidence: all 12 failures carry the same error message: "expected a single document in the stream."

3. **Morning-briefing status:partial is a status-reporting artifact (4/5 runs):** Every morning-briefing run except the first (May 24) reports status:partial, yet all 4 pass all 5 assertions and produce A or B grade output. The partial status reflects connector availability gaps (Clay, Plaud, Jarvis inbox) — not output failure. The composite score penalizes the partial status through the mechanical component, suppressing scores below what the actual output quality warrants.

4. **System-eval never writes a working memory file (5/6 runs):** The assertion `system-eval output contains expected content` fails on 5 of 6 system-eval runs because no memory/working/system-eval-*.md file is ever written. The workflow produces an analysis report and a dashboard, but doesn't write an episodic working memory entry. This is a consistent gap across the entire workflow history.

5. **General-purpose orphaned stubs inflate failure rate (8/43 records = 18.6% of corpus):** All 8 general-purpose records are aborted with 0 steps and no output. The 6 from June 19 (151710, 151711, 155239, 155240, 155721, 155749) appear to be cascade initialization failures from a single session. The 2 from May 29 are similar. These records have no assertion definitions and cannot be graded meaningfully — they artificially pull the batch average down by ~0.06.

6. **Controller feedback collection has stalled (0 new ratings since June 9):** The last 5 controller feedback ratings are all from early corpus entries. No feedback has been collected in 18+ days despite workflows running daily. The eval harness has no mechanism to surface graded-but-unrated records to the controller for feedback.

7. **Daily-review improvement trend is real but fragile (positive):** The 4 most recent output-producing daily-review runs (June 23, 25, 26 scored A, A, B) represent the best sustained performance in the corpus. However, the June 27 run regressed to F (output-write failure), confirming the output-gap bug is still present and will intermittently interrupt the trend.

## Recommendations

1. **Add output-write guard to daily-review step-auto:** The workflow's step-auto completes and writes state.yaml but intermittently skips writing the output file to reviews/daily/. Add an explicit file-existence check at the end of step-auto — if the output file was not written, either retry or set status: failure. Do not allow status: success without confirming the file exists on disk. This affects 6 of 19 runs (31.6%) and is the highest-priority fix in the corpus.

2. **Fix daily-review assertion for state.yaml (update to handle multi-doc YAML):** The assertion engine's `yaml_field_equals` check uses `yaml.safe_load`, which rejects multi-document YAML. Either (a) update the assertion engine to use `yaml.safe_load_all` and read the first document, or (b) update the daily-review workflow to write a single-document state.yaml. This fix would convert 12 false failures to passes and improve the assertion pass rate across all daily-review records retroactively.

3. **Add working memory write to system-eval step-06:** The system-eval workflow produces a dashboard and analysis report but never writes a memory/working/system-eval-*.md file. Add a step-06 action to write a brief working memory entry summarizing the run (records evaluated, batch average, top recommendation). This would fix the failing `system-eval output contains expected content` assertion on all future runs.

4. **Correct morning-briefing mechanical status scoring:** The partial status on morning-briefing artificially degrades the mechanical component score despite A-grade output quality. Either (a) update the workflow to report success when all primary outputs are written (treating connector gaps as logged warnings rather than partial status), or (b) update the score_eval.py to treat partial differently when assertion_rate = 1.0 and grade = A. The current scoring penalizes well-performing runs due to infrastructure availability, not output quality.

5. **Surface graded-but-unrated records to controller at session close:** 38 of 43 records lack controller feedback. The exit behavior in CLAUDE.md already includes an eval feedback sweep — ensure it surfaces records from the last 7 days (not just today) to maximize feedback collection. Target: collect controller ratings on at least 3-5 records per week.

6. **Purge or tag orphaned general-purpose stubs:** The 8 general-purpose aborted stubs (no output, no steps, cascade failures) permanently suppress the corpus batch average. Add a `tags: ["orphaned-stub"]` field to these records and exclude orphaned stubs from batch average computation in score_eval.py. Without them, the functional workflow average is 0.823 — a more accurate picture of system health.
