## Patterns Identified

**1. daily-review silent output failure — recurring (4/10 runs, 40%)**
Runs on 2026-05-30, 2026-06-02, 2026-06-05, and 2026-06-13 all report `status: success` or `partial` but write zero output files (no `reviews/daily/auto-YYYY-MM-DD.md`, no `memory/working/daily-review-*.md`). This pattern has persisted across 3+ weeks despite being flagged in the June 9 analysis. The scheduled workflow runs at ~02:00 UTC — the failure may be session-context dependent (missing calendar data, blank OmniFocus output, or a premature state.yaml close before the output write).

**2. state.yaml timing false-negative — structural noise (11 assertions across 2 workflows)**
Both `daily-review` and `system-eval` assertion definitions check `workflows/{name}/state.yaml: status: complete`. This assertion always fails when a system-eval run is in progress because step-01 sets state.yaml to `in-progress`. This generates false failures for every eval record of these two workflows during every system-eval run. The assertion is testing a global state, not the per-record state.

**3. daily-review working memory file never written in failing runs (6/10 runs)**
On every run where the output file is missing, the working memory file is also missing. These always fail together — confirming this is a single root cause (workflow exits before both writes), not two independent failures.

**4. daily-005-shutdown-section regex too narrow (at least 2/10 runs)**
The pattern `(?i)(completed|done|accomplished|finished|wins)` misses real content: the June 12 review contains "completions", "cleared", and "closed" but none of these match. This inflates the assertion failure count and lowers the assertion pass rate for otherwise good outputs.

**5. system-eval working memory file never written (2/4 runs)**
The `system-eval-009-content` assertion (checking `memory/working/system-eval-*.md`) has failed on both system-eval records assessed this run. No `memory/working/system-eval-*.md` file has ever been written. Step 6 of system-eval does not include a working memory write — this is a documentation/protocol gap, not a runtime failure.

**6. general-purpose records have no assertion definitions (2 records)**
Two records for `general-purpose` tasks have no assertion definition file, so assertion_rate defaults to neutral 0.5. These were manual session runs; they cannot be systematically evaluated without a definition file.

## Recommendations

**1. [CRITICAL] Add minimum-output guard to daily-review step-auto before status close.**
The workflow must verify that `reviews/daily/auto-YYYY-MM-DD.md` exists and is non-empty before writing `status: complete` to state.yaml. If the file is missing, the workflow should set `status: partial` and log the specific failure. This is the same recommendation from the June 9 report — it has not been implemented.

**2. [HIGH] Replace state.yaml timing assertions with per-record output file checks.**
Retire `system-eval-001-state-complete` and `daily-001-state-complete` from their respective assertion definitions. These check global mutable state and will always fail during system-eval runs. Replace with assertions that verify the output files from that specific run (e.g., check for a grading report file timestamped within the run window, or check the eval record's own `completed` field).

**3. [MEDIUM] Broaden `daily-005-shutdown-section` regex to stem-match.**
Change `(?i)(completed|done|accomplished|finished|wins)` to `(?i)(complet|done|accomplish|finish|win|cleared|closed|wrapped)` to capture the actual language the daily-review output uses. This will fix false failures on otherwise high-quality outputs.

**4. [MEDIUM] Add working memory write to system-eval step-06.**
Step 6 should write a `memory/working/system-eval-{date}-{id}.md` summary file before closing the eval record. This will satisfy `system-eval-009-content` and provide a human-readable session log.

**5. [LOW] Add Tier 4 controller feedback prompts for graded records older than 14 days with no rating.**
Records eval-20260524T194258-HBF752 (morning-briefing, grade C), eval-20260526T215647-T3Q5PX (daily-review, grade B), and eval-20260527T021153-F0GRE1 (daily-review, grade C) have grades but no controller feedback. Surface these to David for a quick rating.

**6. [LOW] Create a general-purpose assertion definition.**
Two general-purpose records have no structural assertions. Create `systems/eval-harness/assertions/general-purpose.json` with baseline checks: mechanical completion, at least one output produced, no tool failures. Even generic assertions improve coverage.
