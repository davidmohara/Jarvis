## Recommendations

1. **Investigate daily-review scheduled runs on 2026-05-30, 2026-06-02, and 2026-06-05.** Check daily-review `state.yaml` for those dates, and examine what calendar/data conditions existed. These three dates may share a pattern (e.g., weekend, holiday, no OmniFocus data returned). Add a guard in the workflow: if the review file is not written, set `status: failure`, not `partial` or `success`.

2. **Fix daily-review working memory write step.** The working memory step is failing silently on ~50% of runs. Review the step's file-path construction — if it depends on a date variable that's set incorrectly, the write will fail without surfacing an error. Add an assertion in the workflow itself that checks for working memory file existence before setting `status: complete`.

3. **Fix daily-review state.yaml `complete` transition.** No daily-review run has ever reached `status: complete`. The final step is either not executing or not writing the state update. This is the single highest-confidence bug in the corpus — 8/8 failure rate on a specific assertion.

4. **Add a minimum-output guard to daily-review.** Before exiting with any non-failure status, the workflow should verify that the review file exists and is non-empty. If the file is absent, force `status: failure` and surface the failure explicitly in the eval record.

5. **Create an assertion definition for `general-purpose` agent runs.** Two aborted general-purpose records have no assertion coverage. Even a minimal definition (e.g., checks for session output or inbox action) would give these records structural signal.

6. **Implement a Tier 4 feedback prompt mechanism.** After each workflow run scores below 0.70, surface a one-line prompt to David asking for a thumbs-up/down. The current feedback weight is wasted — 11.76% of the score model contributes nothing.
