## Patterns Identified

1. **[SYSTEMIC] Assertion harness does not inject run_date for date-specific checks.** The `date_specific: true` and `date_path_template` fields in assertion definition files are parsed by the system but not used by step-02-assert's evaluation loop — it falls back to bare glob patterns. This causes any prior-day file to satisfy date-specific assertions. Confirmed: IREQ63 (daily-review 07-25) scored 8/8 assertions with no 07-25 output file in existence. Affects all `date_specific` assertions across daily-review and potentially other workflows. (Evidence: 1 confirmed false-positive; at minimum 13 historical daily-review assertion results should be re-evaluated.)

2. **[REGRESSION] Morning-briefing output write broke between June 26 and July 20.** Four consecutive A-grade runs produced output; the July 20 run produced none. Status remained `partial` in both regimes, so the failure mode isn't visible from status alone. No data source failure is logged in the July 20 eval record. The briefing workflow completed state.yaml but skipped the memory/working/ write. (Evidence: 5 assertion passes in June runs, 1/5 in July 20 run; no error logged in steps array.)

3. **[VOLUME] General-purpose and fork records are polluting the corpus.** 28 aborted records from these categories have zero steps, zero tool calls, and scores averaging 0.21 — pulling the batch average from ~0.78 to 0.62. These appear to be orphaned eval stubs opened but never closed properly. They are not meaningful workflow runs. (Evidence: 28 records with status=aborted, completed=false, steps=[].)

4. **[PATTERN] Daily-review working memory write is absent in ~37% of runs.** 14 of 38 daily-review records fail the working memory assertions. These failures cluster in earlier records (pre-June), suggesting the working memory step was added after the workflow was established. More recent runs (July) all pass. This pattern is resolving naturally but drags the historical average. (Evidence: assertions 2-4 each fail 14 times.)

5. **[BUG] system-eval close-eval-record.py creates spurious records on session_id mismatch.** The July 18 system-eval run produced two records (6D8CK8 and W4CIW9), the second being a duplicate created by close-eval-record.py when session_id didn't match. Sandbox permissions prevented deletion. The spurious record has the same step data as the real record. (Evidence: state.yaml field `spurious_record_reason` for the July 18 run; W4CIW9 and 6D8CK8 share identical started timestamps and step arrays.)

6. **[SIGNAL] Daily-review phantom success on 07-25 (IREQ63).** The daily-review workflow for July 25 reported status=success with step-auto completing in 0 seconds. No review file was written for 2026-07-25. The 0-second step duration is a strong signal that the workflow logic short-circuited or errored without surfacing a failure status. (Evidence: step duration=0.0s, no auto-2026-07-25.md in reviews/daily/, IREQ63 graded F.)

7. **[GAP] Tier 4 controller feedback covers only 10% of the corpus.** The feedback loop depends on David rating runs at session exit, which is skipped in headless mode and inconsistent in interactive sessions. No retroactive feedback mechanism exists. (Evidence: 86 records with feedback.rating=null.)

## Recommendations

1. **[P0] Fix step-02-assert to inject run_date and use `date_path_template` when `date_specific: true`.** The assertion definition schema already includes the mechanism; the evaluator just isn't using it. Update the assertion evaluation loop in the system-eval workflow to read `run_date` from the eval record's `started` field, format it as YYYY-MM-DD, and substitute into `date_path_template` before evaluating. This eliminates false positives from prior-day files. Affects: all daily-review assertions and any future date-specific workflows.

2. **[P0] Investigate and fix morning-briefing output write regression.** The briefing workflow produced A-grade output in four consecutive June runs and nothing in July. Read the morning-briefing workflow file and compare June vs. July execution paths. Add an explicit output-file-existence check before setting state.yaml status to complete. If the write step was conditionally gated on an Obsidian MCP connection that became unavailable in July, add a fallback write to memory/working/ that doesn't depend on MCP availability.

3. **[P1] Investigate daily-review step-auto 0-second completion for IREQ63.** The July 25 daily-review run completed in 0.0 seconds with status=success and no output. This is not a normal run — something caused the workflow to exit immediately. Check the daily-review workflow's state.yaml status check at initialization: if state.yaml had status=in-progress from a prior run, the workflow may have exited early rather than executing. Verify daily-review/state.yaml was reset before the July 25 scheduled run.

4. **[P1] Purge or quarantine orphaned general-purpose and fork records from the scoring corpus.** The 28 aborted stub records are not real workflow runs — they represent failed initialization attempts or test invocations. Scoring them drags the batch average by ~0.16 points and obscures meaningful trends. Either: (a) exclude records with `steps=[]` and `status=aborted` from batch scoring, or (b) move them to a separate `runs/archived/` directory. Either approach would restore the batch average to ~0.78, which better reflects actual system health.

5. **[P1] Fix close-eval-record.py session_id handling to prevent spurious duplicate records.** When session_id doesn't match, the script creates a new record instead of updating the existing one. Add a lookup by session_id before creating a new record, and update in place if a match is found. Alternatively, pass the eval record ID explicitly from state.yaml rather than resolving by session_id.

6. **[P2] Add a minimum step duration guard to daily-review's step-auto.** A 0-second step completion is diagnostic of a skip or crash, not a real run. Add a check: if the step completes in under 5 seconds, log a warning and inspect state before setting status. This would have surfaced the IREQ63 failure as a visible signal rather than a silent phantom success.

7. **[P3] Build a retroactive Tier 4 feedback mechanism.** The exit-behavior rating prompt is the only current feedback path, and it's skipped in headless runs. Consider adding a weekly feedback request to the weekly-system-eval scheduled task: surface the 5 most recent unrated records with grade B or higher and ask David to rate them inline. This would increase Tier 4 coverage from 10% toward a meaningful threshold.
