## What the review found

Four defects in the brand-new skill:

1. `counts.total_uncompleted` returned **258** where the honest count of open
   work is **136**. Two independent causes, both measured live:
   - `flattened tasks` includes each project's root row — 49 phantom rows
     carrying `completed: false`.
   - Archiving a folder in OmniFocus does not complete its tasks. The 21
     projects inside the hidden `Archive` folder hold 73 tasks that stay
     `completed: false` forever.
   Arithmetic reconciled exactly: `258 = 136 open + 73 archived + 49 roots`.
2. The "canonical pull" is `inbox ∪ due-in-7 ∪ flagged` (34 tasks), while
   `counts` reports a different universe under the same skill. Naming only.
3. `workflows/morning-briefing/verify/step-02-gather-tasks.py` read
   `of_data["inbox"]["uncompleted"]` — a key the producer has never written.
   It returned `None` every run and still reported `pass`. Inert since the day
   it was written (an Aug 25 eval record describes it as working).
4. `_simple()` split AppleScript list output on `","`, AppleScript's default
   delimiter. Latent — no current tag or project contains a comma.

## The MCP exercise

Wrote `skills/omnifocus-data/scripts/mcp_client.py` — a minimal MCP stdio
client that spawns `run-server.sh` itself, so the script reaches the MCP
without depending on the session's connection. Diffed real task-ID sets rather
than counts, which is what made the picture legible:

```
258  raw AppleScript = 136 open + 73 archived + 49 project roots
164  raw MCP         = 136 open + 28 project roots
```

The MCP was right about archived work and wrong about project roots (it returns
each project as a row in task queries). Neither raw number was correct.
`query_omnifocus` also returns a *display rendering* that omits `note`, so it
cannot produce the canonical pull — `pull`/`list` stay on AppleScript. The
MCP **resources** do return structured JSON with notes.
